本文档用于帮助接手开发的 Agent 快速理解“工序管理”相关数据表的职责和数据流。这里的“工序管理”不只指后台的工序基础资料页面，还包括工站、报工类别、工艺路线、工单路线指定、现场报工、审批和工站人员限制。

本文不展开字段清单。实际字段和索引以当前数据库、迁移 SQL 和代码查询为准。

## 1. 先看结论

- 工序、工站、报工类别和工艺路线属于配置数据。
- 新增、编辑、启用/停用和路线版本操作先进入 `mo_config_approval_yx`，审批通过后才写正式配置表。
- 待审批或已驳回的新增申请并不在正式配置表中，后台列表是把审批记录中的申请内容合并后展示出来的。
- 工艺路线是版本化数据。已被工单使用的路线不能原地修改步骤或适用类别，应创建新版本。
- 工单实际采用哪条路线，优先看显式绑定，其次看已经形成的执行状态，最后才按产品类别匹配当前路线。
- 执行历史大量保存名称和人员快照。基础资料改名后，不应反向改写历史记录。
- 删除功能已停用，业务配置主要通过启用/停用和路线版本切换管理。

## 2. 数据库边界

| 数据源 | 作用 | 读写性质 |
|---|---|---|
| MySQL `DB2_NAME` | 保存工序配置、路线、审批、工单状态和报工流水 | 管理后台与报工服务共同读写 |
| U8 SQL Server | 提供生产工单、物料、部门和领料资料 | 当前工序模块主要只读 |

管理后台 `jml_admin/webapi` 和小程序报工服务 `JML_MINIAPP/pthonapi` 必须指向同一套 MySQL 现场业务库，否则会出现后台配置已生效、现场端却看不到的情况。

## 3. 核心配置表

### `mo_material_coding_cover_yx`：物料编码规则封面

由管理后台单独维护，固定记录 `id=1` 保存 `title`、`created_by`、`modified_by` 和 `change_history`。变更记录每条包含日历日期 `date` 和可多行的 `description`，最近一条的日期即页面最后修改日期。`revision` 防止覆盖其他用户的新版本，`updated_by`、`updated_at` 记录后台实际保存人和保存时间。初始化入口为 `webapi/init_material_coding_cover.py`。

### `mo_material_coding_category_yx`：物料编码规则分类内容

分类页共用一张表，每个 `page_key` 一条记录。`content` 保存分类的分区、示例列表及分组对照表，可包含分组标题和备注。旧版单条示例在读取时转为示例列表。编码以字符串保存，原有重复编码按行保留。对照项保存编码、说明及废弃状态，导入时优先按对应原表的删除线标记，原始打样资料无删除线的历史条目按「历史使用」标记推定初始状态。`accessory-products` 的 `content.products` 保存序号、名称、图纸编号、工艺和客供材料，PNG 原图存放在后台项目的 `webapi/assets/material-coding/accessory-products`。`revision` 控制并发编辑，`updated_by`、`updated_at` 记录实际保存人和时间。初始化入口及各分类初始资料见 `webapi/init_material_coding_category.py`。

`supplier-abbreviations` 的 `content.suppliers` 保存供应商名称、属性、所售产品、简称和备注。属性和备注允许留空，简称按不区分大小写校验唯一性。

`veneer-design` 的分组记录保存 `image_collection`，编码行可附对应图片文件名列表，同一编码的整图和分片图共用一条记录。数据库保存文件引用，原图由产品图片接口读取过后台校验的四个目录。

### `mo_process_yx`：工序主数据

保存可复用的工序定义，例如裁切、压贴、包装。工艺路线步骤引用这里的工序。停用工序后，不应再用于新路线配置，但已有路线和历史执行记录仍可能引用它。

### `mo_workstation_yx`：工站主数据

保存实际生产位置、设备或作业台。路线步骤通过关系表配置允许使用的工站；现场开工时会记录最终选择的工站。工站人员权限配置也以这张表为入口。

### `bj_product_cost_yx`：报工类别/产品类别主数据

后台“报工类别”页面实际维护的表。工艺路线用它判断适用哪些产品类别，工单再根据 U8 物料上的类别名称匹配内部类别。

注意：该表也被报价/成本功能使用，不是工序模块独占表。修改类别名称或启用状态时，要同时评估报价模块和路线自动匹配。

### `mo_route_yx`：工艺路线及路线版本

保存路线基本信息，也承担路线版本管理。一条业务路线可以有多个版本并行供新工单选择，同一版本组只应有一个默认版本。2026-11-04起 `is_current=1` 表示该组默认版本，不再表示只有该版本可选择；`is_active=1` 表示允许新工单选择该版本，旧版本停用不影响原工单继续执行。`is_default` 仍表示部门默认路线，不能与版本组默认标志混用。部门默认路线、启用状态、版本来源和版本说明都围绕这张表管理。

路线一旦被工单使用，后台不允许直接改动其关键配置，而是通过“新版本”复制原工序进入编辑草稿。用户实际调整工序并点击“提交申请”后，确认是否设为默认版本，再创建审批；未携带工序、工序完全未变化的申请由后端拒绝。审批载荷 `set_default` 保存本次选择。审批通过后才生成正式新版本；选择保留原默认时只新增可选版本，不修改原默认标志或产品类别映射。选择设为默认时同步版本组标志和产品类别默认映射，无默认版本时新版本自动设为默认。已有工单不自动升级。

### `mo_route_step_yx`：路线的有序工序步骤

定义某个路线版本包含哪些工序以及先后顺序。一条路线对应多条步骤，每条步骤引用 `mo_process_yx`。

这是路线版本自己的结构快照。申请新版本时前端复制旧版本步骤供用户调整，审批通过后按申请内容建立新版本步骤，不能把多个路线版本共用成同一组步骤记录。

### `mo_step_station_yx`：路线步骤与允许工站的关系

定义每个路线步骤允许在哪些工站执行。一个步骤可以对应多个工站，一个工站也可以被多个步骤使用。

它依附于 `mo_route_step_yx`，不是直接把工站挂在整条路线或工序主数据上。替换路线步骤时，需要同步处理本表的旧关系。

### `mo_route_version_category_yx`：路线版本适用类别快照

保存每一个路线版本适用的产品类别。历史版本和当前版本可以保留各自的类别配置，用于版本查看和恢复。

这张表是版本维度的事实记录。创建新路线版本时会复制来源版本的适用类别；编辑未使用版本时，更新的是该版本自己的记录。非默认版本的类别调整不改变自动匹配。

### `mo_product_route_yx`：产品类别到当前有效路线的匹配表

提供运行时的快速匹配：当工单没有被人工指定路线时，通过产品类别找到当前应使用的路线。

它不是完整版本历史，也不是全部可选路线表。只有默认版本发生切换或默认版本的适用类别改变时，代码才根据 `mo_route_version_category_yx` 重新同步本表。一个产品类别只保留一个自动匹配版本；全部版本接口通过 `default_product_codes` 返回实际默认类别，工单指定页面不能直接遍历所有版本的适用类别推断默认。Agent 修改路线版本逻辑时，必须同时检查这两张类别关系表是否保持一致。

## 4. 工单与路线绑定表

### `mo_wo_route_yx`：工单行的显式路线绑定

保存管理后台“工单路线指定”的结果。绑定粒度是工单号加工单行号，优先级高于产品类别自动匹配。

未接收、未开工且未形成状态的工单可以调整显式绑定；已进入接收或执行流程的工单不能随意换路线，单条指定、批量指定和取消指定均由WebAPI校验。切换默认版本前，对仅有确认接收记录、还没有工单状态的工单补写原路线绑定，避免首次开工时跟随类别改用新默认；已有手工绑定不覆盖。该绑定补齐与默认版本变更在同一审批事务中提交，不批量替换旧版本。

### `mo_wo_state_yx`：工单行当前工序状态

保存工单当前使用的路线、执行到第几步以及整体状态。它是现场列表、看板和工单详情判断“待开工、进行中、待接收、已完成”的主要状态来源。

这张表只表示当前状态，不代替历史流水。排查数量、人员、照片或每次完工时，应继续查看执行、接收和返工相关表。

路线选择优先级为：

1. `mo_wo_route_yx` 中的显式绑定；
2. `mo_wo_state_yx` 中已经固定的路线；
3. `mo_product_route_yx` 中按产品类别匹配的当前路线。

## 5. 现场执行与历史流水表

### `mo_execution_yx`：工序执行主记录

记录某个工单行在某条路线、某一步骤上的开工和累计完工情况，是现场报工的核心流水表。后台完工查询、生产看板、工序履历和后续交接都以它为主线。

表内保存工序、工站和操作人的快照信息，因此基础资料改名不会改变已经发生的生产历史。

### `mo_execution_completion_yx`：分批完工明细

记录一次执行过程中的每一笔完工提交，包括部分完工和最终完工。`mo_execution_yx` 保存累计结果，本表保存每次提交的明细；排查“累计数量怎么来的”时应查看本表。`photo_url` 保存本批原完工照片，最多5张；`quality_report_photo_urls` 保存本批质量报告单照片JSON数组，最多2张。A1、A2或C数量大于0时，报工API分别要求两组照片至少1张；全部为A时原完工照片选拍、质量报告单允许为空。

### `mo_execution_worker_yx`：开工人员快照

保存某次工序执行选择的作业人员及其当时的人员信息。它属于执行记录的人员明细，不能只依赖当前通讯录反查历史人员。

### `mo_handover_yx`：上下工序交接

上一工序完工后，记录交出到下一工序的数量和接收状态。它把上一工序的完成与下一工序的接收连接起来，是“待接收”状态的主要依据。

### `mo_receive_work_yx`：接收作业记录

用于需要把“接收”作为一段独立作业处理的场景，记录接收开始、接收完成、投入和产出等信息，并关联对应执行记录与交接记录。

### `mo_receive_worker_yx`：接收作业人员快照

保存每次接收作业选择的人员，职责与 `mo_execution_worker_yx` 类似，但归属于接收作业。

### `mo_makeup_record_yx`：追加接收/补录流水

记录接收数量发生的每一次增量变化。交接表和执行表保留累计结果，本表用于解释累计值是经过哪些补接收或追加动作形成的。

### `mo_rework_yx`：返工作业主记录

记录由某次工序执行产生的返工任务及累计返工结果，并关联原始执行记录。返工不是一条新的普通工序路线，而是依附于原执行记录的处理链。

### `mo_rework_completion_yx`：分批返工完工明细

保存返工作业每次完工提交。`mo_rework_yx` 保存累计状态，本表保留逐笔返工产出，作用与普通执行的分批完工表相对应。`photo_url` 保存本批返工完工照片，`quality_report_photo_urls` 保存本批质量报告单，两组照片与普通完工批次使用相同规则并关联具体返工完工批次。

### `mo_rework_worker_yx`：返工人员快照

保存返工作业参与人员及当时的人员信息。

### `mo_execution_print_log_yx`：工序标签打印日志

记录完工或返工标签的打印次数、打印任务和操作人。它不改变工序状态，但后台完工记录会用它显示打印次数并防止同一客户端任务重复计数。

### `mo_operation_log_yx`：工序业务操作明细

按动作保存首工序领料接收、工序接收、开工、分批完工、追加接收、发起返工和返工完工等业务流水。每条记录固定保存操作人、作业人员、工单、工序、工站、本次数量、等级数量、原因和照片快照，供“数据看板 → 工序操作明细”查询。

本表是不可编辑的追溯记录，不代替各业务主表和逐笔完工表。业务动作与日志必须在同一个数据库事务中提交；历史数据通过来源类型和来源记录 ID 回填，无法还原的旧过程不应虚构。

## 6. 工站人员限制相关表

### `mo_station_staff_config_yx`：工站人员配置

为每个工站保存线长和允许扫码报工的员工名单。它扩展 `mo_workstation_yx`，不替代工站主数据。

### `mo_station_staff_exemption_yx`：全局工站豁免名单

保存不受普通工站人员绑定限制的员工名单。豁免仅针对工站报工限制，不等同于管理后台权限，也不能绕过登录、员工启用状态、数量和照片等业务校验。

### `mo_station_access_setting_yx`：工站人员限制及报表开放设置

保存工站人员校验是否启用、配置版本以及小程序报表开放范围 `report_access_mode`。开放范围取值为 `exempt`（仅豁免人员）、`station`（工站授权人员）和 `all`（全部有效员工），默认 `exempt`。关闭工站人员限制时仍保留人员配置；报表开放范围和工站操作总开关分别保存，但报表返回数据始终继续按报工查看范围过滤。

### `mo_station_receive_binding_yx`：接收后固定工站

在接收动作发生后，把交接记录固定到本次选择的工站和员工。后续同一交接的报工继续沿用该工站，避免在执行中途换站。

### `jml_staff`：小程序登录员工

提供现场登录身份、员工状态和显示姓名，也是工站配置及豁免名单选择人员的来源之一。

### `mo_worker_department_scope_yx`、`ding_user_yx`、`ding_department_yx`

这组表用于限定可参与报工的钉钉部门，并提供可选作业人员及部门信息。工序执行、接收和返工的人员快照从当前人员资料生成，但历史记录不应随着通讯录变化而重写。

## 7. 审批、权限与审计表

### `mo_config_approval_yx`：配置变更审批单

统一承载工序、工站、报工类别和工艺路线的新增、编辑、启用/停用、路线新版本及版本恢复申请。它保存申请前快照、申请后内容、申请人、审批人、审批状态、审批意见和修订版本。

关键行为：

- 待审批新增只存在于本表的申请内容中，尚未写入正式配置表；
- 后台管理列表会把待审批/已驳回申请虚拟成一行显示；
- 待审批申请可由申请人修改，修改时校验审批状态和修订版本；
- 驳回后可以修改并重新提交，复用原审批单并增加修订版本；
- 审批通过时，正式配置写入、审批状态更新和审计日志必须在同一个数据库事务中完成；
- 如果申请后正式数据已经变化，不能按旧快照直接通过。

### `mo_admin_role_yx`：后台角色及权限集合

保存后台角色和权限标识。工序、工站、报工类别和路线分别细分查看、新增、编辑、状态调整和审批权限；路线另外包含版本恢复相关权限。

### `mo_admin_account_yx`：统一后台账号

保存后台登录身份，不论来自本地账号还是外部身份认证。审批单通过本表关联申请人和审批人。

### `mo_admin_account_role_yx`：账号与角色关系

把后台账号分配到一个或多个角色。最终权限是账号所拥有角色权限的合并结果。

### `mo_admin_user_yx`：旧本地后台账号

保留本地用户名和密码登录资料，并通过 `mo_admin_account_yx` 接入统一账号体系。新审批或权限逻辑应优先使用统一账号 ID，不能只按用户名关联。

### `mo_admin_audit_log_yx`：后台操作审计

记录配置审批、权限调整以及其他敏感写操作。它用于追责和排错，不是审批状态本身；审批结果以 `mo_config_approval_yx` 为准。

### `mo_admin_page_setting_yx`：后台页面全局开关

保存每个后台页面是否启用。它的优先级高于账号和角色权限：页面停用后，即使账号仍有查看、编辑或审批权限，也不能进入该页面；重新启用后原权限继续生效。页面开关自身固定可用，避免所有入口被关闭后无法恢复。

### `mo_report_email_setting_yx`：全局邮件服务配置

单例表，保存“系统配置 → 基础配置 → 通信服务 → 邮件服务”的SMTP服务器、端口、账号、SSL和加密后的密码。密码密文由Flask密钥派生的Fernet密钥生成，接口只返回是否已设置，不返回密文或明文。报表发送继续读取此全局配置，不另建或复制SMTP数据。

### `mo_report_delivery_setting_yx`：分报表发送配置

以 `report_key` 为主键，分别保存发送开关、手动/定时方式、日/周/月计划、收件人、抄送人、密送人、主题、正文和发送结果。当前报表键包括 `production-dashboard`、`receipt-comparison`、`workorder-process-report`。`last_sent_slot`用于同一计划周期去重；初始配置均关闭，不会因初始化自动发送邮件。

### `mo_approval_email_setting_yx`：审批邮件配置

单例表，保存审批通过即时邮件开关、每周全量清单开关、每周星期与时间、收件人、抄送人、密送人以及并发更新版本。默认收件人为 `yuanxin@goldenchameleon.cn`，两个自动开关初始化为关闭。

### `mo_approval_email_delivery_yx`：审批邮件投递记录

记录即时审批、每周清单及两类手动测试邮件的待发、发送中、成功或失败状态。审批ID和周期键用于自动邮件去重；记录尝试次数、发送时间、主题、收件人及最后错误。审批事务只写入待发记录，SMTP发送由后台任务处理，发送失败不回滚审批。

## 10. Agent 修改代码时必须遵守的规则

1. 不要绕过审批接口直接从管理页面写工序、工站、类别或路线正式表。
2. 待审批列表数据来自审批表合并结果，不能误认为正式表中已有该记录。
3. 不能用基础资料名称作为稳定关联键；关系应沿用现有 ID 或编码。
4. 路线已被工单状态、显式绑定或执行记录使用后，不要原地改步骤，应创建新版本。
5. 切换路线默认版本时，要同步 `mo_product_route_yx`，同时保留 `mo_route_version_category_yx` 的版本快照；新建非默认版本不修改自动匹配。
6. 替换路线步骤时，先考虑 `mo_step_station_yx` 的依赖，避免残留无效工站关系。
7. 不要因为人员、工序或工站改名而批量更新历史快照。
8. 数量问题要同时核对主记录和逐笔明细，不能只看 `mo_execution_yx` 或 `mo_rework_yx` 的累计值。
9. 变更当前状态与写入流水应放在同一事务中，避免出现状态已推进但明细未落库。
10. 常规业务不做硬删除。现有路线删除接口明确返回“删除功能已停用”。
