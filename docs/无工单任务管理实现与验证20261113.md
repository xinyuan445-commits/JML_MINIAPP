## 3. HTTP契约

两套服务均注册 `/api/nonorder`，分别使用各自现有身份入口。小程序API基址仍为现有PythonAPI域名；后台使用本地WebAPI地址。成功响应统一为 `{code:0,success:true,data:...}`；400参数无效、401未登录、403无权、404不存在、409状态／版本冲突、503未启用或不可用。

| 方法及相对路径 | 参数／返回 | 范围 |
| --- | --- | --- |
| GET context | 员工、发布／管理资格、类别、工站、合并去重扫码候选 | 实时读取资格，验证9张表列可读；不自动建表 |
| GET tasks | tab=mine/managed/pending；后台另有transfer | 本人、当前管理、可核对待办；交接入口仅返回必要摘要 |
| GET detail | id=总任务ID | 当前权限过滤后的任务、分工、本人／管理范围记录、时段、已发布安排、操作要求快照 |
| GET people | task_id | 正式负责人或专门交接权限查询代管／接管候选 |
| POST command | 下述统一动作体 | 每次重新校验身份、资格、状态、版本及业务关系 |
| POST attachment | multipart file、task_id、可选display_name | 私有存储，必须已有可访问任务；新任务先保存草稿再附文件 |
| GET attachment | key | 每次按当前任务及记录权限读取，下载禁止缓存；无公开静态直链 |
| GET candidates | date、可选planned_date | 后台范围内候选；发布不自动写安排，保留已开工未完成工作；按指派+日期检查占用 |
| GET daily-result | date | 后台范围内原结果及后续核对／时间修正附记；GET不补存快照 |
| POST /api/admin/accounts/staff-binding | id、revision、staff_id（NULL为解绑） | 账号管理权限，唯一绑定，修改前后值写既有审计 |

所有任务写操作包含：`action`、`request_id`；已有任务另有`task_id`、当前总任务`revision`。同一身份同一请求ID同内容返回原结果；换内容复用请求ID被拒绝。手机网络结果不明时保留原请求ID，禁止自动重试为新请求。成功后重新读取详情。总任务版本同时串行化其分工与个人操作，遇其他员工刚提交也可能提示刷新，这是第一版明确的并发策略。

| action | 特有输入／行为 |
| --- | --- |
| create | 总字段、divisions数组；每分工members含staff_id/responsibility；创建私有草稿 |
| publish | 原草稿及派人资格重新校验；直接发布，无审批、无自动安排 |
| edit_task / add_division / edit_division | 总要求不动态传播；分工修改支持按指派ID传responsibilities；实质变化暂停进行中人员并重新接收，已提交者保留原要求 |
| assign / replace | division_id或assignment_id、member、原因；换人新建，旧指派撤销并保留；replace无member表示只撤销 |
| receive / start / pause | assignment_id；暂停类别及其他说明；个人独立接收开工、唯一运行计时 |
| submit | assignment_id、完成内容、附件；首次／补做须有符合要求的有效时段，补材料保持原工作提交时间 |
| feedback / confirm_feedback | 说明、blocking／record_id；阻塞只暂停本人，回复确认不自动开工 |
| correct_time | 入口assignment_id、原因content、before_segment_ids、proposed_segments；起止为北京时间，全部结束；可跨本人任务，重提可传previous_record_id |
| review | record_id、decision、reason；完成approve/materials/rework/unmet，反馈reply，时间approve/reject；取消后不能补做复活 |
| confirm_division | division_id；逐人通过及历史提交结清后显式确认整体，不能因全员取消自动完成 |
| grant / revoke_grant | 员工及固定权限集合、截止、原因／grant_id；显式代管不等于原工站代理 |
| transfer | 新在用线长、qualification_station_ids、原因；保留发布人，更新当前负责人，撤销原代管 |
| cancel / stop_anomaly | 总任务／分工或停用人员指派、原因；保留历史，以实际处理时间停止时段 |

字段来源、必填、取消和核对业务口径继续以需求文档为准。首版附件支持JPG／PNG／PDF，每份最多10 MB、每条最多9份；照片支持拍照或相册，其他附件从聊天文件选择。服务端验证文件头，不按后缀接受任意内容。

## 4. 权限、事务与历史实现

- 小程序仍用既有缓存的`jml_staff.id`作为staff-id，**没有新增强身份认证**。扫码候选仅来自本人实际线长工站，合并去重，不读取代理／豁免作为任务管理权，也不受旧报工开关关闭而放开。
- 负责人依赖的工站资格完整保留在grant；资格缺失立即拒绝管理。移出扫码名单不撤销已有指派执行权，账号停用拒绝员工操作并标记未停止计时异常。
- 后台当前账号、有效角色、显式新模块权限及员工绑定在新事务内再次读取；全范围查看与核对分开。解绑、撤权及代管到期不沿用旧页面权限。无有效员工绑定可使用显式全范围查看／专门交接，不能冒充线长核对。
- 9表中生成列唯一约束限制一个员工一条运行时段、同分工同人员有效指派、一个待核对完成提交、单一正式负责人、同指派同日一条已发布安排。草稿占用按截止时间读取，不删除锁定草稿。
- 两服务使用同一个MySQL命名锁（数据库名+`:nonorder:v1`），只串行本模块短写事务；旧工单和维修不参加此锁。SQLite专项使用BEGIN IMMEDIATE及真实事务／唯一约束。第一版选择模块级锁简化交叉任务修正及冻结的一致性；大规模并发吞吐尚未压测。
- 保存当前状态、结束时段、工作记录、授权与业务事件在同一事务。事件有效时间在事务最后一次写入统一确定，冻结使用同一锁；原提交和原始时段不覆盖。时间修正新增有效时段并标记被替代关系。
- 每次业务事件保留结构化要求／状态快照，用于补存截止时版本。详情只返回可见要求历史，避免将全任务反复的大JSON直接推给小程序。历史显示仍按当前权限过滤，跨任务修正不能泄漏无权任务的时段。
- 日期计算按北京时间左闭右开；运行时段按截止截取，不在零点关闭。冻结持久化独立于安排单，锁定后读原快照，迟到核对／修正作为附记。当前日查询只计到当前时刻，不能预计至今晚零点。
- `planning.py`仅实现候选读取；`snapshots.py`实现计算、冻结及权限裁剪。阶段5的混合保存必须在同一事务更新daily_item并追加包含其版本的任务事件；快照工作进程尚未接线，不能认为此时生产会自动生成新结果。

## 5. 数据结构与后续接线要求

权威定义：`JML_MINIAPP/nonorder_shared/nonorder_core/schema.py`。仍为批准的9张新表；实际数据库未建表。总任务另含创建人／发布人／当前负责人姓名快照；事件时间使用MySQL DATETIME(6)，员工ID为VARCHAR(64)并精确比较。表名与已确认设计保持一致。

权威迁移工具：`python -m nonorder_core.migrate`默认只输出9张表DDL，不连接数据库；只有`--apply --config-env <现有配置路径> --database-name <对应DB2_NAME>`才读取指定现有配置并迁移。本轮未运行apply。工具不导入整个app，不创建连接池副作用，不复制凭据，不自动赋予角色，不写业务样例。账号字段按存在性补充；9表按存在性创建；daily_item关联既有独立安排单，删除受限。MySQL DDL隐式提交，不能承诺一键事务回滚；重复执行与部分失败恢复尚需隔离MySQL验证。

两服务现有连接都来自各自DB2配置；共用包不维护第三套数据库凭据。仓库开发环境通过适配器定位同一份共用包；后续分目录部署时应将同一版本 `JML_MINIAPP/nonorder_shared` 构建／安装到两个服务环境，而不是只传一个routes文件。两个服务requirements新增SQLAlchemy依赖，共用包声明完整运行依赖。

`NONORDER_ENABLED`默认非1，接口关闭且现场入口隐藏。后续完整部署、结构验收和业务验证通过后才能显式启用。附件另需`NONORDER_ATTACHMENT_DIR`为绝对私有路径；两个服务须访问同一份私有存储，不能挂公开静态目录。此环境变量只有路径，没有数据库凭据。本轮没有创建真实上传目录或修改实际.env。

停止新功能优先关闭开关并保留数据；不得删表、重置员工指派、清理旧快照或回滚原业务数据。小程序上传由用户操作。
