## 1. 整体安排

无工单任务独立存储，复用人员、工站、后台账号角色及每日安排单。不在ERP中生成虚构工单，不把无工单报工混入现有正常／返工执行表，不改维修表。

用户已确认采用9张新表方案，并在现有后台账号表增加可空员工绑定字段：7张任务业务／历史表、1张无工单日安排明细、1张每日冻结结果。此前12张设计已被本版替代；尚未建表，因此没有合表迁移或历史数据搬动。具体边界默认规则及本轮复核补充见第8节，仍属于可调整的设计细化。

完成提交、问题反馈、时间修正均属于“员工发起、管理人处理、保留轮次”的工作记录，合并为一张有固定类型的工作记录表。后台账号与员工的一对一绑定直接扩展现有账号表，历史沿用既有后台审计。无需另建员工表、工站表、类别管理表或发布审批表。

```text
总任务 task
 ├─ 分工 division
 │   └─ 个人指派 assignment（换人建立新记录，旧记录保留）
 │       ├─ 工作时段 time_segment
 │       ├─ 工作记录 work_record（完成提交／问题反馈／时间修正）
 │       └─ 日安排 daily_item ── 现有每日安排单 sheet
 ├─ 明确任务管理授权 manager_grant
 └─ 业务事件 event（变更、接收、交接、核对等不可覆盖快照）

每日冻结 daily_result：不依赖是否存在安排单
后台账号 account.staff_id（可空、唯一） ── jml_staff
```

## 2. 核心任务与执行表

### 2.1 `mo_nonorder_task_yx`：总任务

- `id`、唯一 `task_no`；`content`、`category_code`、`acceptance_standard`、`planned_date`、可空 `due_at`、`remark`、`attachments`。
- `creator_staff_id`、`publisher_staff_id`、`responsible_staff_id`（当前负责线长）；姓名快照仅显示，关联和权限使用ID。
- 创建／发布时间、状态、`revision`、取消原因／时间；恢复取消任务改为另建时可记录 `source_task_id`。
- 原发布人不随交接改写；当前负责人改变与授权及交接事件在一个事务内提交。

### 2.2 `mo_nonorder_division_yx`：分工

- `id`、`task_id`、分工序号、内容、标准、类别、可空 `station_id`、计划日期、截止时间、备注及附件、排序、状态、`revision`。
- 建立时默认带入总任务字段，保存为分工自己的有效值；第一版不建设动态字段继承系统。发布后改变总任务不自动传播，线长显式选择受影响分工，展示差异并按职责变更规则处理。
- 无工站用NULL，不使用0或伪造工站；无工站分组由当前负责线长产生，不用作权限身份。
- 整体确认人、确认时间和结果事件，不能单凭个人状态数推断线长已确认整体标准。

### 2.3 `mo_nonorder_assignment_yx`：个人指派

- `id`、`division_id`、`staff_id`、姓名快照、本人职责、当前要求版本及快照、已接收要求版本、状态、`revision`。
- 首次接收／最近重新接收时间、撤销时间和原因、`replaces_assignment_id`（交接来源）。每次接收事件单独留痕。
- 同一分工同一员工最多一条有效指派。换人不更新旧记录的员工ID，而是终止旧指派并建立新指派，以免历史时间和提交转归新人。
- 指派时保存实际资格来源及当时范围快照；原线长来源工站设计需补充豁免来源与线长本人指派的表达。后续新增／换人仍读取当前权限，不用旧快照永久授权；具体扩展见第8.6节待实施建议。
- 管理资格来源和执行资格分开：员工仍有效且未撤销的既有指派默认允许继续；移出扫码候选名单阻止新增指派，不删除原执行记录。账号停用则拒绝执行，待有权人员处理。

### 2.4 `mo_nonorder_time_segment_yx`：工作时段

- `id`、`assignment_id`、`staff_id`、要求版本、`started_at`、可空 `ended_at`、结束原因、实际操作人、来源类型。
- 来源区分真实点击与已批准修正；`correction_id`、`superseded_by_correction_id`连接修正关系。原始时段只在正常结束时落结束时间，后续不覆盖原起止值。
- 批准修正后新增有效时段并标记被替代时段；拆段、补段、剔除误操作均能保留原记录。修正得到的时段必须已结束，不生成运行中的计时器。
- 按员工锁定并使用唯一约束保证最多一个未结束时段；暂停、变更职责、换人、取消和提交完成与时段结束同事务处理。
- 唯一计时及重叠限制范围为本无工单模块，不跨模块拦截原工单报工或维修；不会为本次功能改变旧执行接口。
- 用时从有效时段计算，不维护可手改的累计小时数。跨日按北京时间区间切分，不必每天复制原时段。
- 同一员工已批准有效时段不允许重叠；补记错任务须同一修正申请处理两边，通过时整体校验及生效。

### 2.5 `mo_nonorder_work_record_yx`：完成提交、问题反馈与时间修正

三类记录共用一张表，但使用固定 `record_type` 区分，各自保留业务校验，不建设可配置的通用审批平台。

- 共用普通列：`id`、`record_type`、入口 `task_id`、`assignment_id`、`staff_id`、要求版本、内容／原因、附件、提交人及时间、处理状态、处理人及后台账号、处理时间／意见、`previous_record_id`、`revision`。
- 按类型与状态、指派、员工建立查询索引；关键查询字段不藏在JSON中。少量专用列允许为空，时间修正提案等变长内容保存为结构化JSON。
- 提交内容与当时要求快照不可覆盖。状态及当前处理结果条件更新，并在同事务中追加业务事件，保证历史截止状态可追溯；重提新增记录并关联上一轮。

| 固定类型 | 特有内容和规则 |
| --- | --- |
| `completion` 完成提交 | 职责／标准及提交时用时快照、实际完成内容、异常说明、退回类型（补材料／补做）。同一指派不能重复存在待核对完成提交；新修正用时另算，不覆盖提交证据 |
| `feedback` 问题反馈 | 是否阻塞本人、线长回复、员工确认时间。阻塞反馈与结束本人时段同事务；多次回复追加事件，重新提问新增关联记录；处理后不自动开工 |
| `time_correction` 时间修正 | `before_segments`、`proposed_segments`保存时段ID、原版本、拟定时段及所属指派。批准后才替代有效工作时段，不能通过修改JSON直接改变累计用时 |

时间修正额外约束：

- 可以覆盖本人多个受影响任务，入口任务和指派只定位申请入口；服务端必须校验提案内全部指派，不允许生成未指派任务的工作时间。
- 一份申请由对全部受影响任务有核对权的人确认；跨负责人时先明确共同授权人，不允许只确认一半就生效。
- 每个原时段最多一份待处理申请，按员工锁串行检查全部待处理时间提案及原时段版本；通过时再检查权限、重叠及版本，整体生效。
- 时段表的 `correction_id`、`superseded_by_correction_id`关联本表的时间修正记录，服务端验证其类型和通过状态。
- 合表不合并状态流转：反馈已解决不能当成成果已通过，成果通过不能自动批准时间修正；核对权限按记录类型及所有受影响任务校验。

### 2.6 `mo_nonorder_manager_grant_yx`：明确的任务管理授权

- `id`、`task_id`、`staff_id`、授权类型（当前负责人／临时代管／历史事项接管）、权限集合、有效起止时间、撤销时间、授权来源、操作者及原因。
- 负责人指针与有效负责人授权一致，任务同一时刻只有一位正式负责人；代管可以并行但必须明确授权。权限包括任务调整、成果核对、时间核对，代管默认不含再次转授权或正式交接权。
- 工站代理不自动生成任务授权。豁免身份提供新任务发布和全配置人员候选资格，创建自己的任务时明确建立负责人授权；不自动生成他人任务的管理／核对授权。读取时检查有效期、员工状态及授权是否被撤销，不依赖过期清理进程。
- 普通负责线长从工站线长身份获得的资格消失时，停止相应管理权并提示交接；不能仅看本表仍有旧记录就继续放行。临时代管按明确任务授权校验，不要求其同时为工站线长。
- 正式接管人原设计为在用线长，其派人按自己当前范围、历史核对限明确交接任务；是否扩展至有效豁免人员及其资格来源处理见第8.6节待确认建议，不沿用旧设计限制豁免新任务发布。
- 交接默认由有权原负责人或专门交接权限后台人员明确确认后生效，接管人获知；不增设审批链。原负责人失权不能自行转授权。

### 2.7 `mo_nonorder_event_yx`：不可覆盖的业务事件及版本快照

- `id`、`task_id`、可空分工／指派／来源记录ID、事件类型、操作者来源、员工ID／后台账号ID、姓名快照、发生时间、原因、变更前后JSON、要求版本、幂等请求标识。
- 记录发布、职责版本、接收、暂停原因、反馈、提交核对、时间修正、指派撤销、交接和日安排变更等。
- 状态表用于当前查询，工作记录表保存提交与待办，事件保存每次处理及变更事实；时段独立计算，不依靠自由文本日志反推业务状态。
- 实际执行核对的操作者身份与来源由服务端确定，不接受客户端伪造实际核对人。用户可按业务规则选择将来负责核对的候选人员，服务端校验并留授权事件；这与冒充实际操作者不同。后台和员工双身份操作同时留痕。
- 小型附件数组随对应业务记录保存URL、名称、类型等；不另建通用附件管理系统，文件访问沿业务权限检查。

## 3. 接入每日任务的两张表

### 3.1 `mo_nonorder_daily_item_yx`：无工单日安排明细

- `id`、`sheet_id` → 现有 `mo_daily_task_sheet_yx`、`assignment_id`、`work_date`、可空 `station_id`、当前负责线长快照、顺序、备注、发布状态、取消状态、`revision`、创建／发布时间及操作者。
- `snapshot`保存安排时任务、分工、人员职责、类别、工站和线长资料。无需工单号、路线、安排数量、质量等级，也不伪造ERP部门。
- 一条明细对应一个个人指派在一天的安排，同一指派同一日期在主单和补充单间最多一条已发布有效安排；未锁定服务器草稿暂时保留位置防重复，取消后释放。已经锁定且未发布的草稿不再占用位置，但原记录／快照保留，允许在补充单正式安排；占用资格由截止时间判定，不依赖清理旧记录。
- 第一版只有已发布的日安排才对员工显示并参与已安排实绩匹配；保存未发布属于服务器草稿。已发布安排的允许修改在保存后生效。任务发布与每日安排发布是两个动作。
- 后台混合草稿可统一保存／发布，工单部分沿既有校验，无工单部分按独立身份校验，整个保存保持原子性和跨日截止复核。
- 不把新记录ID塞入原工单明细ID。前端、缓存、接口使用来源类型＋ID区分，并兼容旧草稿，不清理旧缓存。
- 不改动原 `mo_daily_task_item_yx` 的工单必填列；原内部部门表 `mo_daily_task_yx` 留给工单，无工单直接关联独立安排单，不设虚假部门行。
- 共用既有安排单的锁定时间，计划／结果快照以可选 `nonorder_items` 等新段扩展；旧JSON缺字段按空处理，不重写旧快照。工单实绩计算分支保留。
- 同一人同一分工当天的多次计时、补做、提交均汇总一次；同日重复换人再换回使用不同指派ID，各自保留责任和时段，不串账。

### 3.2 `mo_nonorder_daily_result_yx`：每日无工单冻结结果

- `work_date`唯一、`cutoff_at`、`frozen_at`、`schema_version`、`result_data`；按日期保存全部无工单执行及其安排归属、资料和核对状态，再由API按权限裁剪。
- 独立于安排单，解决当天没有任何安排单仍有实际执行的情况；不能为生成结果自动新建空安排单。
- 执行次日零点冻结，跨零点仍计时的时段按截止点截取当日用时，下一日继续原时段。全部安排单及未安排执行使用同一份日期实绩，避免归属不一致和重复统计。
- 日期冻结结果是无工单当日实绩的唯一固定来源。安排单 `result_data` 只保存该日期快照引用及本单明细映射，不再另存可独立变化的无工单实绩副本；读取／导出在后端组合并过滤权限。旧工单结果结构不变。冻结时使用同一锁和事务规则，避免先冻结日期后创建补单改变历史归属。
- 锁定后的时间修正、迟到核对和任务变更单独查询工作记录／事件展示，不覆盖 `result_data`，不当成新一天的执行。
- 持久事件及提交版本用于还原截止时已有事实；停机补存记录真实生成时间。缺失原始历史无法还原时明确提示，不伪造准点冻结。
- 冻结范围包含有效安排但零执行、未安排执行、安排取消但有执行，以及当日提交／核对事件；没有任何数据的日期返回空，不预建每日空记录。工作时段和当天核对事件分栏，不能把核对算为当天执行。

## 4. 后台身份绑定与权限默认设计

### 4.1 在现有 `mo_admin_account_yx` 扩展员工绑定，不另建表

- 增加可空且唯一的 `staff_id` → `jml_staff.id`，以及绑定版本、绑定人和绑定时间。一个账号最多绑定一名员工，一名员工最多绑定一个账号；既有账号默认为NULL，不影响原登录及其他模块。
- 由有账号管理权限人员显式维护，绑定／解绑的前后值写入既有 `mo_admin_audit_log_yx`。不按姓名、用户名、手机号自动推断；解绑或账号／员工停用即时停止后台员工身份操作。
- 解绑后当前 `staff_id` 置空，但原绑定历史从审计可追溯。核对等业务事件另存操作当时的账号ID及员工ID，不依赖当前绑定反查过去身份。
- 此绑定只标明同一个人，不授予工站权限、派人权或任务核对权。并发绑定检查版本及唯一约束，不覆盖其他人员刚修改的绑定。

### 4.2 三种权限分开

| 能力 | 默认规则 |
| --- | --- |
| 后台查看／安排 | 需要现有每日任务页面权限，并另外明确授权无工单查看／安排权限；本人管理范围通过绑定员工的有效任务授权计算；全范围PMC查看／安排使用单独的全范围权限，不因绑定自动获得 |
| 线长核对／时间修正确认 | 后台需明确核对入口权限＋有效员工绑定＋具体任务的当前核对权；全范围安排人员、系统管理员、豁免人员不因此自动获得他人任务的业务核对权 |
| 正式交接／指定代管 | 原有权负责人按规则操作；后台兜底要求专门任务交接权限。该权限允许交接，不自动允许代核对或代员工报工 |

不自动扩大已有角色权限。角色标识拟使用 `nonorder.view/manage/review/transfer` 及独立 `nonorder.view-all/manage-all`，最终名称在实施前与权限定义对齐。范围内返回的候选、统计、名单、详情、附件、历史、导出均做同一过滤。本人范围的混合安排单仅显示有权明细，不泄漏其他范围数据或依靠客户端隐藏；保存采用显式变更集合，不把未返回行当删除，也不发布无权部分。

后端每次操作重查账号、员工、任务授权、到期和版本；小程序与后台调用同一套任务业务权限规则，两端不各自实现不同判定。

## 5. 剩余事项的第一版默认选择

以下为用户授权Agent拟定的默认设计，可调整，不误记为此前逐项确认。

- 暂停原因必选简短类别：休息、等待材料、等待配合、临时调配、其他；其他必填说明。职责反馈、线长调整自动记录专用原因。
- 关联工站由任务管理人维护，后台排期不改变工站，只允许拖到原关联工站或对应无工站分组。变更工站按职责影响核对，不自动迁移历史安排。
- 只有正式发布的每日安排参与员工日期展示和实绩匹配；未发布服务器草稿不算已安排，提供“已存草稿未发布”提示。此规则细化需求文档中“保存后归类”，需发布后才正式归类。
- 一份完整任务的正式交接不按单个工站自动拆给多个新线长；需要拆分时显式调整分工。无工站任务按当前负责人分组，历史快照仍为当时负责人。
- 指派已完成／撤销、总任务取消后，未来安排标为不再需要执行，保留原安排，不自动删除或改写锁定计划；未锁定部分由有权人员确认撤销。员工端不继续显示为可执行待办。
- 草稿任务不交给员工执行；新增分工完整保存后按已发布任务变更进入候选，不自动排日期。发布后任务内容不完整的变更不能保存生效。
- 同一日期全部实绩只归属一次；无已发布有效安排但有取消安排时标记“安排已取消·有执行”，否则未安排，保留草稿提示。主单展示全日未安排汇总，补充单不重复计入；按日期入口可独立查询。
- 打印在同一安排单下分工单、无工单两段；Excel分工单、无工单、后续修正Sheet。无工单展示工站／当前负责人、任务／分工、人员职责、日期、状态、用时与核对结果，不占用数量等级列。冻结结果与修正分开，浅蓝表头、深蓝粗体。
- 第一版不并入既有工单报表、生产看板、标签或维修页面；小程序在无工单模块查本人工作及线长待核对。站内待办和变化提示优先，不默认发送微信订阅消息、短信或邮件。
- 小程序仅因任务操作权限总开关的旧工单规则关闭，不应开放所有员工发布新任务；无工单发布要求有效线长或豁免资格，具体任务管理按明确授权。此规则独立于旧工单权限开关，不改旧流程。
- 岗位或工站配置变化不删除历史。撤权如何判定须以实际配置及员工状态为准，不能依赖姓名或原发布字段；部分工站撤权影响的现行负责人授权应提示交接或重新明确授权，不能用其仍负责另一工站自动保留全部管理权。

## 6. 数据约束与边界

- 新表主键拟为BIGINT；员工ID沿现有 `VARCHAR(64)` 约定，工站／后台账号ID与对应现有主键一致，最终DDL前核对实际类型。
- 名称、职责、标准、权限来源保存快照用于追溯；当前权限永远读取当前资格及明确任务授权。
- 核心关联和可筛选字段为普通列；JSON仅用于附件列表、修正提案、版本证据、锁定快照，不把所有关系塞进一列。
- 业务时间统一北京时间语义，并分别记录实际发生时间、提交记录时间、核对生效时间，避免回填时间越过冻结截止而污染历史。
- 状态变化、时段结束、业务事件、交接和授权在同一事务；使用revision和幂等标识防旧页面覆盖及重复点击，按员工锁防双计时，按安排日期及指派校验跨单重复。
- 保留记录，取消／撤销用状态及事件，不硬删除。新模块字段、接口和状态不会冒充原工单号、路线步骤或正常／返工种类。
- 原每日任务代码仍需增加读取合并、保存、权限及快照扩展，不能声称完全不动后台代码；目标是不改变原工单规则，后续实施须针对混合保存、旧草稿、零点锁定、权限和去重作回归验证。
- 本文不执行真实初始化、迁移或数据写入；已编写结构定义不等于实际业务库已有这些表。

## 8. 整体复核：补齐边界与验收要求

本节为用户授权范围内的设计细化，修正歧义，不新增数据表、业务模块或实施授权。需求文档第13节同步业务口径。

### 8.1 权限：当前授权决定能否访问，历史快照只证明当时事实

- 任务详情、冻结JSON、后续修正、附件和打印导出均按当前有效权限过滤。已到期代理不能凭历史授权继续查看全任务；原发布人撤权后也不因名字仍在快照中放行。
- 员工默认仅查看本人的职责、工作记录、用时与必要公共任务要求，不返回同事反馈、附件或时段。负责人查看其明确管理的完整任务；交接权限可读取处理交接所需的任务摘要和候选负责人，不等同全量成果或附件查看权。
- 明确代管权限只有固定的任务调整、成果核对、时间核对三项，不设计通用授权规则编辑器。代管没有线长资格／有效派人范围时可处理反馈与核对，但不能新增或换人指派；不能借用原线长的名单冒充自己的派人权限。
- 正式交接时显示并默认撤销旧代管授权，需要保留的明确重授；历史操作不删。任何身份在核对保存时已到期／撤销，均拒绝旧页面提交。
- 本人可能同时为扫码人员与任务管理人。默认禁止确认自己的完成提交及时间修正，负责人本人执行须按新增规则另选核对人，其他人员由符合具体事项授权的人处理；有权后台人员只能安排接管，不能凭交接权限直接代核对。
- 原线长负责人授权保存 `qualification_station_ids`（本任务管理资格依赖的工站）；新豁免来源不能以空工站集合冒充通过，来源扩展见第8.6节。原工站来源规则为：保存依赖工站，不使用其无关工站自动续权。集合包含关联工站及用于本次指派资格的工站，多个可用来源取实际选定来源；正式接管时重新明确资格依据。依赖资格撤销导致负责人授权不可用，进入待交接，不撤销员工既有有效指派。
- 员工账号停用与移出扫码名单分开：停用拒绝新执行操作，移出候选名单不自动抹掉原指派。停用时尚有运行计时必须列异常待处理；由明确有权人员终止，记录真实处理时间；实际停工时间需修正申请／核实，不能默认截成离职或午夜时间。没有停用事件准确时间时不得伪造。
- 后台身份绑定属于有授权能力的管理操作，不允许普通账号自行绑定他人员工。跨账号绑定唯一性、解绑生效及旧会话每次重查纳入验收，现有凭据模型不被描述成新增强认证。

### 8.2 锁定：三种状态和两种时钟不得混用

- 任务发布、日安排发布、员工执行状态独立。已发布任务可以未安排执行；已保存未发布安排不能误认为正式计划；已发布安排不等于员工接收。
- 安排锁定使用创建日期次日00:00，结果锁定使用执行日期次日00:00，均为北京时间，区间采用左闭右开。服务器时间及生效顺序为准，不接受客户端传入的发布／核对时间作为历史归属。
- 保存跨安排截止，整次安排事务拒绝，含无工单明细；员工执行和线长核对不随日安排锁死。执行跨日继续记录，零点后的核对仅作为后续事项展示。
- 时间修正按批准生效时点判断是否能进入当日冻结：截止前申请但截止后批准，原日结果仍保留批准前有效时段。补存时查询“截止前有效版本”，不能直接用当前状态或当前 `superseded_by_correction_id`过滤，须结合批准生效事件。
- 对跨零点未结束时段只计算截止前那部分，不关闭原计时器；恰在00:00发生的开工归新一天。补记到此前完全没有快照的历史日期，原历史基准为空／零执行，补记作为后续修正，不能冒充当日已存在的事实。
- 运行中的计时、核对及修正提交与冻结须有明确的短事务串行边界；事件使用服务端记录时间及生效版本，冻结不读取未提交事务。跨零点事务及停机补存必须验证，不能只按提交者填写的业务时间回放。
- 历史快照不读取当前姓名、工站、职责、负责人或授权覆盖显示。当前负责人分组用于当前任务视图，历史打印使用当时保存的负责人；当前权限仍单独检查。
- 日安排唯一归属基于 `assignment_id + work_date`，全日候选检查覆盖主单和补充单。取消后重排同一人的当日实绩归当前有效正式安排一次，取消单保留“有执行、现归其他安排”提示，不重复累计。
- 冻结后不重分配实绩。迟到时间修正按受影响日期及原指派列附记，不覆盖原日明细或归属。

### 8.3 历史与状态：取消、换人、版本变化不能形成死路

- 分工完成检查针对当前仍需履行的有效指派；已撤销／被替换的旧指派不永远卡住完成，但其待核对历史提交必须明确处理。全员撤销或全部分工取消不能因“无待办”自动判为完成，须取消或重新安排。
- 取消任务后仍可核对取消前提交、补充事实材料及申请时间修正；补材料不能重新计时。核对不合格但已取消时记录未达标及取消原因并结束该历史待办，不允许“退回补做”自动复活已取消任务。确需继续施工另建关联任务。
- 仅有待核对提交不代表一定发生了有效开工：首轮完成须存在本人已接收职责下的工作时段；漏记可先申请补记并获确认。补材料重提无需新时段，补做重提须有新的工作时段。计时全部因误操作被剔除时标记结果待核查，不静默删除原已通过结论。
- `requirement_revision`与一般保存并发版本分开。改备注／日期可增加并发版本，不强迫重新接收；实质要求变化才增加职责版本，时段及提交指向当时职责快照。
- 重提保留 `previous_record_id`；前后记录必须同本人、同业务类型及合法指派关系，不能把问题反馈链到完成提交。待核对记录只能被成功处理一次，反馈员工确认不得覆盖新一轮职责变化。
- 总任务执行历时不作为个人工时：界面分别显示首次开工、最近工作提交及最终核对。退回补材料不延长工作执行结束时间；退回补做按新工作段／工作提交延长。修正个人工时不改原点击时间，避免一个指标同时代表两种含义。
- 附件沿对应业务记录权限读取，引用已提交／冻结记录的附件不得因页面删除或换人直接清理；第一版不承诺公开直链具备访问控制，实施前须核实存储与授权读取能力。

### 8.4 控制复杂度

- 保持9张表，不新增通用审批、动态表单、自动排程、通用代理继承或工序依赖系统。
- 总任务默认值只在建立时带入，之后显式修改；不实现多层实时继承。
- 全日无工单实绩只有日期冻结表一个固定来源，安排单不再维护第二份可变化副本。
- 混合页面保存仅提交明确变更、独立校验两种任务身份；限权账号不使用旧整单覆盖方式提交未见明细。界面显示实际保存／发布范围，不能把发布本范围写成已发布整单。原工单接口兼容与混合事务失败回滚均需验证。
- 跨任务错记时间涉及不同核对人时不增设多人审批流程，仍由明确拥有所有受影响任务时间核对权的人一次处理；可以只授时间核对权，不为纠错授全部任务管理权。

### 8.6 新确认规则与授权衔接复核（仅文档，待确认部分不作为定案）

**已确认业务**：发布人与指派候选按需求第3节区分；负责人本人执行时，总任务另选一名受限核对人，该人不能是本任务执行人员；负责本人提交、反馈、时间修正及相关分工整体确认，不能自核对，也不因此获得任务调整、换人、取消或转授权权。现有原代码仅提供整任务授权，不能直接认为已支持此范围。

**拟实现方式，尚未定数据库字段／迁移**：

- 保持9张表，不增加第10张“审批表”。拟复用 `manager_grant` 记录固定类型的本人执行核对授权，任务层展示一名当前核对人；历史授权留有效期、撤销原因和事件，不覆盖旧核对人。
- 授权需要明确核对对象和可确认的分工范围。不能只给现有 `review/time_review` 整任务权限，也不能只在前端隐藏其他人员；详情、工作记录、时段、附件、待办及跨任务修正均由服务端按具体事项过滤。分工整体确认只开放必要要求、人员核对状态及必要结果，不因此默认开放无关人员全部附件和时间明细。
- 核对对象拟关联稳定员工／指派及历史来源，不仅根据当前 `responsible_staff_id` 动态推导，防止交接使原负责人历史核对丢失。具体按员工或指派保存，待交接规则确认后决定；不提前增加通用权限表达式。
- 新增负责人资格来源需区分线长工站与豁免；普通线长自指派也要保留实际资格依据。当前 `qualification_station_ids` 只足以表达工站来源，不使用空集合放行豁免。创建／发布／交接时记录明确来源，后续每次操作重查，来源失效后的重新确认或交接流程见需求第3节建议。
- 一人兼有普通代管和特殊核对授权时，建议分别记录、分别撤销。总权限计算仍先拒绝自核对，再校验特殊事项归属和具体授权，不能简单并集后开放整项核对。
- 交接建议继续默认撤销普通代管，但显式选择特殊核对人继续或更换，确认覆盖原／新负责人相关事项后，与负责人及授权变化同事务生效。换核对人不重写提交当时要求、已做时段、实际历史核对人或冻结结果。
- 豁免人员候选明确来自工站配置的全部线长／扫码人员，不推断额外员工；停用人员不得新指派。停用工站上的配置是否仍计入“全部配置人员”、豁免新增分工可关联哪些工站，尚需明确，不能暗中扩大为全部员工或全部工站。
- 特殊核对人回复职责问题不等于有权改职责；需修改要求时仍由有任务调整权的人操作并走重新接收。跨任务纠错仍需一人对全部受影响事项有权；普通代管不能绕过指定核对人，若存在冲突应显式协调授权。

待确认业务以[需求第3节](无工单任务管理需求.md)为准，不自动实施上述建议。后续验收至少覆盖：豁免发布但不可访问他人任务、普通线长自指派且未指定核对人被拦截、特殊核对人不能核对无关人员／访问无关附件、普通代管不可绕过指定核对、负责人交接前后的历史提交均有归属、核对人失效或加入执行、交接与核对并发、自核对拒绝、跨任务时间修正和跨日冻结原值保留。


### 8.7 权限调整最终落地（同日后续，替代8.6中的待定实现方式）

用户已确认代管与交接规则，本轮完成本地实现。仍为9表，扩展 `mo_nonorder_manager_grant_yx`：

- `qualification_source`：station／exempt，默认station兼容原授权；豁免来源实时校验豁免名单，工站来源继续校验明确依赖工站，不自动跨身份续权。
- `review_staff_ids`：可空JSON，self_review授权保存所核对原／新负责人的稳定员工ID；核对对象通过对应任务内指派关联，交接后不丢历史归属。
- `reviewer_task`：仅未撤销self_review授权生成任务ID，唯一索引 `uq_nonorder_reviewer` 保证同任务一名当前核对人；失效但未撤销的旧授权需显式替换。
- self_review与owner、delegate独立；普通代管撤销命令只接受delegate。更换核对人撤销旧self_review并新增，交接明确核对人后将旧授权撤销、重新建立，全部变化与事件在同一事务。

资格、权限和读取过滤由共用包 `review_permissions.py` 与service处理，客户端不能用整任务review权限绕过受限核对。待办、详情、附件沿具体记录权限；受限核对人仅返回保护对象的指派／时段／记录，相关分工其他成员仅显示姓名和完成状态。跨任务时间修正要求对所有受影响任务的同一执行人员均有核对权。

显式迁移工具已增加重复可执行的ALTER与索引检测；本轮只在临时SQLite和MySQL DDL编译中验证，未执行真实MySQL迁移，旧线上服务尚不具备这些新增规则。共用包版本0.2.0。
